### AOB

#### Intent to implement process

jdm: People have been talking to me about WebIDL integrations that don't fall under baseline. I don't want to give people false hope. I am working on a proposal for what we intend to ship / expect to merge. If people have any thoughts feel free to chat with me.

jdm: Main concerns: Things that will never become cross browsers standardized, things that never get completed, people putting effort into things that won't get merged. If there are other issues, feel free to raise them with me.

nico: Kind of related: I've been doing a bunch of work on visualizing WPT test results for blitz. Pulls in the format -- makes obvious where there are gaps in Servo. Would it be useful to write up an analysis where there are big gaps.

martin: if there are things like big gaps, it'd make sense to continue on that issue: [servo/servo#24828](https://github.com/servo/servo/issues/24828)

emilio: I'm mostly curious that what are the particular features that triggered this?

jdm: I know that Shubham was interested in WebNN support and there another contributor that's going to be doing a stint at the Recurse Center who is interested in WebHID and WebUSB.

emilio: Those are tricky. Issues like maintenance.

martin: one other thing that kind of mentioned josh, but similar to what emilio has said, is that new features need maintenance, who is going to be responsible when it's broken and we need to fix things

jdm: I'm aiming for a low process proposal to Zulip. Who is the primary entity doing it / who is the primary entity to contact in the future.

martin: how do we know when we turn a feature on? when is it done in the sense that we can turn it on? how many tests need to pass before "is done"?

jdm: I agree with those. I do think that this is under a separate proposal for having a more consistent process for when do we ship things so that we don't go API by API for when to turn things on by default.

nico: Feels like we are being too conservative. People can't use Servo because there are gaps.

nico: The quicker the better, right?

martin: to some extent I agree, the more code the hard is to move towards baseline, if the tests are flaky or you have to refactor a lot of code for unrelated things that are not baseline

emilio: I agree with Nico that if things are baseline and stable enough (doesn't crash / cause regressions on other pages), then those things can probably be turned on. The point is I agree with Nico, but you have to distinguish between features that help the whole project versus random things that are very cool. Each feature may add more burden than its worth, you have to weigh things. If you have to refactor the WebIDL bindings, you might run into trouble. For high benefit, low risk features as soon as it's ready, stable, it's time to gather feedback.

nico: I definitely agree there aught to be a distinction between core features / ancillary features. That's one thing holding Servo back at the moment is that there is no stable core that's not flaky or crashy.

emilio: Are there numbers around crashiness / flakiness?

martin: we do fuzz servo, I've been prioritizing fixing crashes, most of the crashes are panics; there are other panics that happen in WPT that we haven't looked at

nico: I'm looking at all of the flaky WPT tests. I don't how common those are with mainstream browsers, but in Blitz we don't have any flaky WPT tests. It takes a lot of uncertainty out of the development.

nico: It's one of the cases that makes me question our LLM policy.

martin: to clarify, there's no rule to use LLM to do code analysis in Servo

rego: Next step is what Josh was announcing. Sharing things soon for "intent to implement" and we can iterate on that discussion.
